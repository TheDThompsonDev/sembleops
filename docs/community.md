# Community guide

Welcome to the SembleOps community. Whether you are running your first self-hosted application or regularly maintain production systems, there is useful work you can contribute.

## Start here

1. Read the [README](../README.md), [security policy](../SECURITY.md), and [Code of Conduct](../CODE_OF_CONDUCT.md).
2. Run SembleOps locally with fake or personal development data.
3. Search existing issues and pull requests before opening something new.
4. Start with a small, reviewable problem.
5. Read [CONTRIBUTING.md](../CONTRIBUTING.md) before submitting a pull request.

If you are unsure where to begin, useful starter work often includes:

- correcting an unclear setup or deployment step;
- reproducing a bug on another operating system;
- adding a regression test for an existing behavior;
- reviewing keyboard navigation, semantics, contrast, or reduced motion;
- replacing a brittle assumption with a clearer error message;
- documenting a safe self-hosting pattern without adding a hosted dependency.

## Choosing the right channel

### Community Discord

Use an official community Discord for introductions, demos, informal peer support, and shaping an idea before it becomes work. Do not treat Discord as the project database or a private support contract.

Never paste API keys, bearer tokens, cookies, `.env` files, databases, private prompts, task data, proprietary code, access links, or unredacted logs. Project maintainers will not ask for those materials in a direct message.

### GitHub issues

Use the guided issue forms for reproducible bugs, focused feature proposals, and documentation gaps. An issue should contain enough public, synthetic context for someone outside Discord to understand it.

Open an issue before beginning a large change. A maintainer response can prevent duplicated work or an implementation that conflicts with the trust model. Comment before taking an issue, keep progress visible, and say when you can no longer continue so someone else may help.

### Pull requests

Connect a pull request to a defined problem and keep it focused. Draft pull requests are welcome for early technical feedback, but they still must not contain secrets or private data. Review is best-effort, and submission does not guarantee merge or a particular timeline.

### Private security reports

Use GitHub's private vulnerability reporting flow for suspected vulnerabilities. Do not disclose a vulnerability in Discord, an issue, a discussion, or a public pull request. Follow [SECURITY.md](../SECURITY.md).

## From conversation to contribution

A healthy path from Discord to the repository is:

1. Discuss the user problem without sharing sensitive data.
2. Search GitHub for related work.
3. Open or update an issue with the durable summary and acceptance criteria.
4. Confirm scope before a large implementation.
5. Submit a focused, tested, DCO-signed pull request.
6. Help review and verify the result.

This keeps participation open to people in different time zones and to contributors who choose not to join Discord.

## Community boundaries

SembleOps is provided without warranty, managed hosting, or guaranteed support. Community members volunteer their time. Be patient, avoid repeated direct messages, and do not pressure an individual contributor for free operational work.

Operators remain responsible for their own credentials, infrastructure, data, backups, provider charges, and compliance. See [SUPPORT.md](../SUPPORT.md) and [GOVERNANCE.md](../GOVERNANCE.md).
